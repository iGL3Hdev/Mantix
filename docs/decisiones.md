# Mantix — Registro de decisiones

Cada decisión relevante se anota con fecha y motivo. Las más recientes van arriba.

| Fecha      | Decisión                                                                                                                                            | Motivo                                                                           |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 2026-10-18 | No se crea la etiqueta `v0.1-landing`; el paso 1 se cierra sin ella.                                                                                | Aporta poco: el estado de la landing se puede recuperar desde el commit `40276b1`. |
| 2026-10-18 | Errores en formato `ProblemDetail` (RFC 9457), con los campos `codigo` (`RN-xx` si se incumple una regla) y `errores`.                              | Es un estándar y Spring lo trae de serie; los tests comprueban el `codigo`.      |
| 2026-10-18 | En el MVP, el usuario que hace la acción se indica con la cabecera `X-Usuario-Id`.                                                                  | Spring Security la sustituye en la fase 2 sin tocar endpoints ni DTO.            |
| 2026-10-18 | Los cambios de estado se hacen con un endpoint `POST` por acción (`/ordenes/{id}/validar`), no con `PATCH` del estado.                              | Cada acción tiene su cuerpo y su regla; se corresponde con la tabla de acciones. |
| 2026-10-18 | Cada fila del historial apunta con `origen_id` a la fila principal de la acción que la provocó.                                                     | Los cambios automáticos se pueden consultar sin depender de un texto.            |
| 2026-10-18 | `historial_estado` pasa a llamarse `historial`, con `accion`, `valor_anterior` y `valor_nuevo`. Registra altas y cambios de estado, prioridad y técnico, pero no las ediciones descriptivas. | Una sola tabla para cualquier evento del flujo; se amplía sin migraciones.       |
| 2026-10-18 | El responsable puede cambiar la prioridad de una incidencia sin cerrar; el estado del equipo se vuelve a evaluar.                                    | Quien abre la incidencia no siempre acierta con la prioridad.                    |
| 2026-10-18 | La baja de un equipo exige que no tenga incidencias sin cerrar y se puede revertir con un motivo.                                                   | Sirve para corregir errores sin crear el equipo de nuevo.                        |
| 2026-10-18 | Un equipo pasa a `AVERIADO` cuando tiene una incidencia `CRITICA` sin cerrar, y vuelve a `OPERATIVO` cuando ya no le queda ninguna. Sus cambios de estado van al historial. | Regla automática entre entidades, sencilla de testear.                           |
| 2026-10-18 | Solo el responsable asigna órdenes; un técnico no puede autoasignarse.                                                                              | Separa con claridad lo que hace cada perfil, de cara a los permisos de la fase 2. |
| 2026-10-18 | La incidencia se cierra automáticamente al cerrar su orden; se reabre a mano con un motivo.                                                         | Evita validar dos veces el mismo trabajo.                                        |
| 2026-10-18 | La orden resuelta la valida el responsable (`RESUELTA` → `CERRADA`) o la rechaza (vuelve a `EN_CURSO`). Las órdenes cerradas no se reabren.         | Da trabajo real a los dos perfiles; la reapertura se hace en la incidencia.      |
| 2026-10-18 | Historial de estados en una tabla polimórfica (`tipo_entidad` + `entidad_id`).                                                                      | Añadir historial a entidades nuevas no exige migraciones; la integridad la garantiza `HistorialService`. |
| 2026-10-18 | El equipo tiene estado operativo: `OPERATIVO`, `AVERIADO`, `BAJA`. Los equipos no se borran.                                                       | Conecta las incidencias con el equipo y conserva el histórico.                   |
| 2026-10-18 | Ubicaciones en lista plana.                                                                                                                         | Basta para el MVP; la jerarquía se puede añadir con `ubicacion_padre_id`.        |
| 2026-10-18 | Una incidencia puede tener varias órdenes de trabajo, pero solo una sin cerrar a la vez.                                                            | Es más realista (una reparación puede fallar) y añade una regla de negocio para testear. |
| 2026-10-18 | La documentación, incluida la especificación del backend (`docs/backend.md`), vive en `docs/` de `Mantix` y no se mueve al repositorio del backend. | Un solo sitio para consultar todo el proyecto.                                   |
| 2026-10-18 | Dos repositorios: `Mantix` (frontend, mantiene su nombre) y `mantix-backend`.                                                                       | Cada uno tiene su propio ciclo de versiones; renombrar el actual no aporta nada. |
| 2026-10-18 | Trabajo directo en `main`, con commit y push al final del día o al cerrar un paso.                                                                  | Proyecto individual; no hace falta el flujo de ramas.                            |
| 2026-10-18 | Perfiles técnico y responsable desde el MVP.                                                                                                        | Para registrar quién hace cada cambio.                                           |
| 2026-10-18 | Base de datos MySQL.                                                                                                                                | Stack ya conocido.                                                               |
| 2026-10-18 | Tailwind CSS en toda la aplicación.                                                                                                                 | Coherencia con la landing, que fija la identidad visual.                         |
